# Durable BCH integration

The unreleased `OpalBaseCore` product provides ordinary BCH accounts, public-chain synchronization, transaction review and exact submission without linking CashFusion or Mosaic. Import `OpalBaseCore` to select that boundary. The existing `OpalBase` product remains a compatibility umbrella that re-exports the same core types and the existing macOS privacy integrations. Package resolution may still include OpalFusion; resolution, compilation, linkage and runtime activation are separate observations. This source change moves type ownership between modules and does not promise binary compatibility.

## Review, finalize and submit

Prepare a `Account.SpendPlan`, then call `review(network:)`. Its `BCHSpendReview` freezes the unsigned envelope, input set, output ordering, fee, change and `templateDigest`. The review uses fixed-size Schnorr placeholders and does not sign. After the application authorizes that exact review, `finalize(network:)` signs that same template and returns a cached `FinalizedBCHTransaction`. Repeated review/finalization of a live lease preserves its original template and bytes. Never rebuild a retained payment to retry it.

`FinalizedBCHTransaction` retains canonical raw bytes, hash, network, selected inputs, fee and optional change. Its public restoration initializer validates complete canonical decoding, BCH-only accounting and input identity. It does not validate signatures, establish authority, recover a reservation or prove prior relay. Store the exact bytes and input/change evidence under the application's durable operation identity before admission.

`claimAndHandoff(_:using:admission:)` enters the address-book actor, then synchronously invokes `BCHSubmissionAdmission`. The middleware receives the actual nonescaping claim-and-begin closure. Hold the application's serialized command/continuity authority lock while checking current authority and invoking that closure, and return its exact invocation handle. The closure validates the live lease, exact current input payloads/reservation ownership, bounded frontier where applicable, and the retained finalized bytes; it claims the lease and hands off without suspension. An authorize callback that returns before a later handoff is insufficient. Do not retain the closure or invoke it twice.

`TransactionRelay.begin` synchronously transfers ownership of exactly one invocation and returns `TransactionRelayAttempt`. A custom `begin` closure is nonthrowing: it must accept ownership before returning and must never retry. Invocation failures belong in the attempt's asynchronous result, so a synchronous throw cannot conceal a completed handoff. The supplied transaction-client adapter starts exactly one async request. Network emission and reply may occur later; they are outside the ordered admission step. Await `attempt.value()` outside the lock. `cancelAndWait()` cancels and waits for local completion, without proving the remote outcome.

After a successful reply, `BCHRelayOutcome` preserves the accepted hash even if reservation completion fails; inspect `reservationCompletionError` and reconcile. A post-handoff error, cancellation or timeout does not prove non-submission. A claimed lease cannot expire, be cancelled, be reused or be replaced by a snapshot. The application must retain its durable spending restriction across uncertainty, restart and failed cleanup. On restart, invalidate unsubmitted preparations; snapshots never recreate live lease authority. A separately admitted relay of retained bytes uses `TransactionRelay.begin` without pretending to restore a first-submission lease.

After an unknown relay, affirmative complete transaction/input/change reconciliation may dispose its local claim through `SpendPlan.completeClaimedReservationAfterReconciliation()`. Base retains the exact invocation owned by that claim, cancels and waits for its local end, then revalidates claim/change ownership before releasing reservation markers. It preserves the currently synchronized UTXO inventory: a conflicting spend may consume only one selected input while others remain unspent. The caller owns the chain-evidence predicate and durable spending gate; this method neither establishes chain evidence nor signs or relays. A concrete earlier completion failure blocks this disposal path; it must remain visible to the application rather than becoming a successful receipt by omission.

The existing `buildTransaction` and `buildAndBroadcast` APIs remain available for compatibility. They do not provide the durable review/atomic-admission contract; `buildAndBroadcast` builds at call time and retains its legacy throwing cleanup behavior.

## Bounded address frontier

`refreshConfirmedAddressFrontier(network:using:)` scans each branch freshly from zero until twenty consecutive addresses lack validated confirmed history. It ignores local used/reserved flags, balance, and mempool-only history. Positive history entries must have a valid transaction identifier and matching internally consistent confirmed transaction status. The injected provider's association/history and chain view remain trusted inputs; this is not independent canonical-chain validation or proof of complete provider coverage.

`ConfirmedAddressFrontier` binds account, network, per-branch highest reachable confirmed index and a process-local revision. Each branch starts at `H = -1`. `boundedReceivingAddress(at:frontier:)` accepts only an index at most `H_r + 20`; the first window is indices zero through nineteen. The application owns durable issued high-water `I_r`, distinct request bindings and atomic disclosure: issue `I_r + 1` only within the bound, commit its durable binding before disclosure, and never lower or recycle high-water after cancellation or expiry. Retrying the same retained request returns its original allocation. This API does not label an address as never issued.

`prepareBoundedSpend(_:frontier:feePolicy:)` selects only `H_c + 1` for change, independently of receive history. It does not silently fall back to another change index. A live or uncertain payment holds that candidate; provably unsubmitted cancellation and accepted no-change completion do not burn it. Confirmed history advances the candidate. Local reservation flags and an unconfirmed change output cannot do so.

Chain refresh mutations make frontier evidence require a new scan. Call `invalidateConfirmedAddressFrontier()` on relevant provider/view or chain invalidation too. A failed or incomplete scan blocks dependent preparation/finalization/handoff. A completed scan with unchanged branch bounds preserves its material revision; changing a bound invalidates dependent unsubmitted plans. The application still owns freshness, source/view identity, reorganization detection and durable evidence restrictions.

Continue monitoring every published address for late deposits. Seed-only recovery must use a genuinely fresh book and this fixed discovery gap. It cannot reconstruct issued-but-unpaid addresses or their request bindings, so metadata loss cannot reset high-water silently. Reorganizations may remove the history supporting a later window: retain issued ranges and history evidence for directed reconciliation, block further issuance/preparation, and do not promise seed-only completeness under arbitrary history removal. Additional accounts, derivation paths or passphrases need a separately defined recovery promise.
